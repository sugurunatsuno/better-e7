# 映像上でタスクと状態モデルを編集する

## 状態

実装方針として提案。2026-09-05の要件確認を反映した作業指示書です。新機能の実装はまだ行っていません。

## 背景

既存アプリには映像プレビュー、Rule editor、汎用AutomationProfile、GameStateがあります。一方、画面へ操作を配置する機能、順序付きタスク、操作記録、画像とOCRに基づく状態モデルの編集はありません。

利用者はタップ位置や矢印を置く方法と、実操作を記録して修正する方法の両方を求めています。状態モデルには画面状態だけでなく、スタミナなどのアプリ内情報も必要です。

## 判断

- 既存eguiアプリを拡張し、映像と編集overlayを同じ画面へ描く。
- 接続と自動化開始を分離し、編集 / 手動操作 / 記録 / ドライラン / 実行の入力経路をruntimeでも分離する。
- 既存のv1 Ruleは保持し、v2に宣言型状態モデルと順序付きタスクを追加する。priorityやcooldownを順序制御へ流用しない。
- GameStateのcurrent / previous / revisionを再利用し、宣言型の推定状態を反映する最小APIを追加する。
- 観測値には型と品質と更新時刻を持たせ、タスク変数と区別する。
- OCRは外部Tesseract processを専用crateへ隔離する案を採用し、実画像評価後にバージョンと学習データを固定する。
- 入力完了通知をIDで対応付け、入力先の実座標系と映像の座標系を区別する。
- 保存は実行用TOMLを確定点とし、編集配置と参照画像を別の編集情報へ保存する。

## 代替案

| 案 | 判断理由 |
|---|---|
| Tauri / Electron / ブラウザGUIを新設 | 既存の映像、egui、runtimeとの重複が増えるため採用しない |
| 別scrcpyウィンドウへoverlay | ウィンドウ位置やOS固有の合成へ依存するため採用しない |
| 既存Ruleだけで手順を表す | 認識tickと入力完了は異なり、順序や停止を表現しにくいため採用しない |
| 既存Dispatcherへすべてを押し込む | 現在は時刻と入力完了通知がないため、SequenceEngineを分離する |
| OCRをOS固有APIへ依存させる | 3OSで条件や結果が変わるため初期採用しない |
| OCRをcloudへ送る | オフライン利用とローカルな画面処理の要件に合わないため採用しない |
| TesseractをFFIで組み込む | native依存と配布が増えるため、最初は既存FFmpegと同じ外部process方式にする |

## 依存と保守

egui / eframe、serde / toml、image、Tokioは既存依存を使います。今回の文書コミットでは依存を追加しません。OCR実装時はTesseract本体と学習データの導入手順、3OSでの起動確認、ライセンス表示、更新時の評価セットを追加します。Rust 1.88と既存workspaceのビルド条件を維持します。

内容hashや原子的置換のために新しい外部crateが必要になった場合も、実装前に候補、必要性、Rustの対応版、ライセンスをこのADRへ追記します。`unsafe_code = forbid`を回避するための場当たり的なunsafe追加はしません。

## 影響

既存の映像プレビューとRule編集を再利用できますが、接続のライフサイクル、入力結果、保存方式には変更が必要です。GUIから状態名を付けるだけではなく、判定の根拠と値の有効性まで実装することになります。

Tesseractが実際のゲーム画像を十分に読めるか、Androidごとの入力座標系を確実に取得できるかは検証課題として残ります。詳細は[設計](../task-studio/design.md)と[実装計画](../task-studio/implementation-plan.md)に記載します。
